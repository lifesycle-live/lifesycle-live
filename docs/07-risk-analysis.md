> known gaps as of `PROGRESS.md` — DB is Supabase Postgres (not Oracle, corrected

## Legal / privacy risk

- **Recording consent**: live broadcasts capture the agent, potentially the property owner/occupants, and viewer comments containing personal data (names, phone numbers volunteered in chat). Consent and disclosure requirements (e.g., UK/EU GDPR, and equivalent regimes wherever Lifesycle operates) must be addressed before recording starts — likely a pre-broadcast consent/disclosure step in the product, not just a policy document.
- **GDPR lawful basis for comment-to-lead conversion**: turning a viewer's platform comment (name, and often a phone number or address volunteered in chat) into a CRM `Lead`/`Contact` record is processing of personal data under GDPR Art. 4(1), triggered the moment `ingestionService.ts` persists an `EngagementEvent`. The two realistic lawful bases are consent (Art. 6(1)(a) — the commenter affirmatively opts in, e.g. by replying to the CTA link Lifesycle posts) or legitimate interest (Art. 6(1)(f) — the agent's interest in following up on an inbound sales inquiry, balanced against the commenter's expectations). A comment made in an open public livestream chat is a weaker consent signal than a form submission, so legitimate interest is the more defensible basis for *raw comment capture*, with explicit consent sought at the point a comment converts to a lead requiring follow-up (name/phone/email). Either way this needs documentation (a Record of Processing Activities entry), not just a Privacy Policy sentence. Transparency/Art. 12–14 disclosure obligations are the EDPB's explicit 2026 Coordinated Enforcement Framework focus across 25 EU data protection authorities, which raises near-term enforcement odds for exactly this kind of "we quietly capture chat as leads" flow if the privacy notice isn't clear and timely [[GDPR compliant live chat]](https://helpsquad.com/blog/gdpr-compliance/).
- **Platform ToS risk on comment polling itself, independent of GDPR**: `ingestionService.ts` polls each configured adapter every ~1s via `fetchComments`, which must go through each platform's *official* Graph/Data API, not scraping. This matters because Meta's Platform Terms explicitly prohibit "access[ing] or collect[ing] data from our Products using automated means (without our prior permission)" and Meta runs a 100+ person "External Data Misuse" enforcement team; the Facebook/Instagram adapters are safe specifically *because* they use App-Review-gated Graph API calls with a Page access token, not a scraper — but this makes the [Meta App Review approval risk above] doubly load-bearing: without it, there is no compliant way to read Facebook comments at all, official API or otherwise [[Meta Automated Data Collection Terms]](https://www.facebook.com/legal/automated_data_collection_terms) [[Facebook Graph API automate without approval pain]](https://www.codewords.ai/blog/facebook-graph-api). YouTube's Data API Terms separately restrict how long comment/API data may be cached — "as long as necessary for purposes consistent with user consent," with a documented deletion path, and a June 2026 policy update added stricter data-retention and derived-metrics disclosure requirements for audited developers with analytics use cases — worth revisiting once Lifesycle's YouTube usage grows past the current single-verified-platform status, since sustained comment storage in `EngagementEvent` rows is exactly the kind of retained "API Data" these terms govern [[YouTube API Services Developer Policies]](https://developers.google.com/youtube/terms/developer-policies) [[YouTube Terms revision history]](https://developers.google.com/youtube/terms/revision-history).
- **Comment/lead data provenance**: converting a public platform comment into a CRM lead record means importing personal data from a third-party platform into Lifesycle's systems. This needs a documented lawful basis (see above) and should respect each platform's developer terms on data use and retention (not just general privacy law) — Meta and Google both impose their own data-use restrictions on API-sourced data in their developer agreements, independent of GDPR.
- **Minors and safeguarding**: open comment sections on public listings can include anyone; standard platform-level moderation tools (see below) need to be paired with Lifesycle's own basic content-safety filtering before AI auto-converts a comment into a lead record.
- **Cross-border data transfer**: if Lifesycle's ingest/storage infrastructure is hosted outside the customer's jurisdiction, standard cross-border transfer safeguards apply to both the video recordings and the captured engagement data. Concretely: Supabase's default project region and any managed streaming vendor's storage region (see [11](11-infrastructure.md)) should be chosen consciously per customer base, not left at a provider default.
- **Token-at-rest encryption is itself a GDPR Art. 32 ("security of processing") concern**, not just a generic security best practice — storing live OAuth tokens to agents' Facebook/YouTube/Zoom accounts in plaintext is a documentable gap against the "appropriate technical measures" requirement and should be named as such internally, not filed purely as an engineering ticket.

## Moderation risk

- Platforms differ sharply in what moderation tooling is exposed: Facebook and YouTube both expose real API-level comment/ban controls (comment CRUD, `liveChatBans`/`liveChatModerators`); Instagram is standard comment tools only (no live-specific moderation API found in research); TikTok has none available to a third party at all [[YouTube moderation]](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts) — see [05](05-api-research.md) cross-platform table.
- **Mitigation**: build one moderation UX in Lifesycle that operates uniformly over the normalized `EngagementEvent` stream (hide/flag/convert-to-lead), and let each adapter implement "push the hide/ban action back to the source platform" only where the platform actually supports it — falling back to "hide within Lifesycle only" elsewhere. This must be surfaced honestly in the UI (agents need to know when a "hide" only hides locally vs. also hides on the live platform).
- **Reputational risk**: an offensive or off-topic comment left unmoderated on a Lifesycle-orchestrated broadcast reflects on both the agent and the Lifesycle brand — moderation latency (webhook-driven platforms will be much faster than poll-driven ones) should be an explicit product SLA per platform.
- **Fair Housing Act exposure is a real, non-hypothetical liability channel specific to real estate, and it is broader than "don't write a bad ad"**: the FHA (US) makes it unlawful to "print or publish" a discriminatory housing advertisement, and courts/HUD have applied that to anyone who *publishes* discriminatory content, not only the original author — a broker can be held accountable for content shared through their own account even when a licensee or a viewer, not the broker, wrote it [[NFHA Responsible Advertising]](https://nationalfairhousing.org/responsibleadvertising/) [[Housing Equality Center — Discriminatory Advertising]](https://www.equalhousing.org/fair-housing-topics/discriminatory-advertising/). This is directly relevant to Lifesycle because viewer *comments* on a listing broadcast are visible on the agent's own live video (and, once converted, live inside the CRM as a `Lead`/`EngagementEvent` tied to that broadcast) — a viewer commenting something discriminatory about who should/shouldn't live in the property, left unmoderated on the agent's stream, creates a facially different but adjacent exposure to the agent's own discriminatory-ad liability. DOJ's active oversight of Meta's own housing-ad ad-delivery algorithm (United States v. Meta, court-ordered compliance period running through June 27, 2026) signals this remains a live enforcement area for housing content specifically on Meta platforms right now, not a dormant 2022-era case [[Houston Law Review — Facebook housing discrimination]](https://houstonlawreview.org/article/12762-contemporary-housing-discrimination-facebook-targeted-advertising-and-the-fair-housing-act).
  - **Mitigation, concretely for this product**: (1) the AI intent classifier (`aiService.classifyIntent`) should be evaluated for whether it can also flag a comment as `flagged_content`/discriminatory-language-risk, distinct from lead-intent classification, so agents get a proactive prompt to hide it rather than discovering it later; (2) the uniform moderation UX above (hide/flag) needs to be fast enough to matter — a comment sitting visible on a live public broadcast for minutes before an agent notices is the exposure window; (3) product/legal copy should make clear to agents that *they*, not Lifesycle, are responsible for moderating discriminatory viewer comments on their own broadcasts, mirroring how brokers are already told they're responsible for licensee-posted content — but Lifesycle's tooling should make fast moderation genuinely easy, since "we gave you a hide button" is a better position than "we surfaced comments with no moderation tooling at all."

## Platform dependency / business risk

- The product's differentiated value depends on API access Lifesycle does not control. A single platform's policy shift can invalidate a chunk of the roadmap with no notice — this already happened in-market in January 2026 to comparable third-party streaming tools on TikTok.
- **Mitigation strategy**: 
  1. Never present any single platform's integration as mission-critical to the core value proposition — the CRM-native lead capture and AI assistance must hold value even if every "assisted" (non-one-click) platform integration were removed tomorrow.
  2. Maintain adapter health monitoring and a clear internal escalation path when a platform's API behavior changes.
  3. Budget ongoing engineering capacity for adapter maintenance as a permanent cost line (see [14-cost-estimation.md](14-cost-estimation.md)), not a one-time build.
