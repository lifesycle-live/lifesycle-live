# 05 — API Research

Per-platform detail on authentication, ingest, chat/comments, webhooks, moderation, recording, and limits. This is the evidence base behind the verdicts in [04-technical-feasibility.md](04-technical-feasibility.md).

> **2026 refresh note**: this doc was re-verified in September 2026 against live developer documentation. Facebook, YouTube, and Zoom now have **real adapter implementations** in `server/src/adapters/` (`facebook.ts`, `youtube.ts`, `zoom.ts`) — ahead of what this doc originally described. Per-platform sections below now note where the *implemented* behavior differs from the original research, and where 2026 platform changes affect either. LinkedIn/Instagram/TikTok remain unimplemented (no adapter) and unchanged in verdict, with updated citations.

## Facebook (Meta Graph API / Live Video API)

- **Auth**: Standard Meta app + OAuth 2.0. There is **no single "Live Video Publishing" permission gate** as such in the current docs — access is composed from ordinary Graph permissions checked per-endpoint: `publish_video` for a user-profile broadcast, `pages_manage_posts` + `pages_read_engagement` for a Page broadcast, all subject to standard **Meta App Review** before non-tester accounts can use them [[Live Video API]](https://developers.facebook.com/docs/live-video-api/) [[Page Live Videos ref]](https://developers.facebook.com/docs/graph-api/reference/page/live_videos/). Page access tokens obtained via a User token with `pages_show_list` do not expire on their own (matches the implementation's assumption in `oauth/facebook.ts` that no refresh token is stored) — only short-lived User tokens expire (~1-2h) before being exchanged.
- **New 2026 eligibility gate (not in the original doc)**: as of June 10, 2024 (still in force in 2026), Meta requires the **Facebook account be ≥60 days old** and the **Page/professional profile have ≥100 followers** before it can go live via the API — a real-world gate to flag to agents whose test/demo Pages are new [[Live Video API]](https://developers.facebook.com/docs/live-video-api/).
- **Ingest**: RTMPS only (not plain RTMP), confirmed unchanged. The implemented adapter (`server/src/adapters/facebook.ts`) receives a single `stream_url` field from `POST /{page-id}/live_videos` and splits it into `rtmpUrl`/`streamKey` at the last `/` — this matches the documented single combined endpoint pattern (`rtmps://rtmp-api.facebook.com:443/rtmp/<key>`), not a separate server+key pair [[RTMPS on Port 443]](https://wrasse.plymouth.ac.uk/ac-news/facebooks-rtmps-live-api-on-port-443-a-secure-streaming-solution-oxxyhl).
- **Publishing flow**: `POST /{page-id}/live_videos` with `status=LIVE_NOW` (as implemented) creates the broadcast and returns the stream key immediately — matches the doc's create → push → end flow. Ending is `POST /{live-video-id}` with `end_live_video=true`, also as implemented [[Page Live Videos ref]](https://developers.facebook.com/docs/graph-api/reference/page/live_videos/) [[User Live Videos ref]](https://developers.facebook.com/docs/graph-api/reference/user/live_videos/).
- **Chat/comments**: `GET/POST /{video-id}/comments` confirmed current. The implemented adapter **polls** this edge (`filter=stream&order=reverse_chronological&since=<ts>`) rather than using Page Webhooks — real-time push via **Page Webhooks** (`live_comments` field) remains available and documented as the lower-latency option but is not what's wired up today; worth reconsidering if comment latency becomes a complaint, since ingestion currently polls every 6s per `ingestionService.ts` [[Webhooks comment sync]](https://reintech.io/blog/real-time-comment-sync-facebook-webhooks) [[Real-time comment listener example]](https://medium.com/emojot-engineering/building-a-real-time-facebook-page-comment-listener-using-webhooks-node-js-graph-api-17dad90e992e).
- **Rate limits (new detail)**: two systems apply — the **Platform rate limit** (`200 × daily active users` calls/rolling hour, app-token scoped) and, for Page/system-user tokens, the **Business Use Case (BUC) limit** (`4,800 × engaged users`/24h). Both are exposed via response headers (`X-App-Usage`, `X-Business-Use-Case-Usage`) rather than a fixed number — worth polling/logging these headers once agent volume grows, since a low-follower demo Page could throttle sooner than expected [[Rate Limiting]](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/).
- **Moderation**: standard comment moderation endpoints (hide/delete/reply) available at the comment-object level; no dedicated "live moderation" endpoint beyond normal comment CRUD. Unchanged.
- **Recording/VOD**: live videos persist as standard Page/User video objects after the broadcast ends and are retrievable through the normal Video API. Unchanged.
- **Verdict feed into 04**: full one-click capability, now **actually implemented** (`FacebookAdapter`) — publish, poll-based engagement capture, and end-of-broadcast handling all work against documented, generally-available endpoints. The only material gap vs. the original research is that comment capture is polling, not webhook-pushed.

## YouTube (YouTube Live Streaming API v3)

- **Auth**: Google OAuth 2.0. As implemented (`server/src/services/youtubeOAuth.ts`, per `docs/18`), the app currently authenticates with **one project-level refresh token stored in `.env`**, not yet a per-agent connection — the per-agent OAuth path described in `18-platform-integration-plan.md` §3.3/§5 is designed but not wired into `YoutubeAdapter.publish()` yet (`_context: PublishContext` is accepted but unused). Standard Google OAuth refresh tokens don't expire from age alone but can be invalidated (7-day limit lifted once the OAuth consent screen is in "Production" / verified status, unlimited test users otherwise) [[Google OAuth 2.0]](https://developers.google.com/identity/protocols/oauth2).
- **Ingest**: RTMPS confirmed current. Flow matches the implementation exactly: `liveStreams.insert` (provision ingest URL/key) → `liveBroadcasts.insert` (create broadcast) → `liveBroadcasts.bind` (attach). The adapter additionally sets `enableAutoStart`/`enableAutoStop: true` so YouTube auto-transitions to live the instant the encoder connects, avoiding a manual `transition` call at start (only `end()` calls `liveBroadcasts.transition` with `broadcastStatus=complete`) [[LiveBroadcasts docs]](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts) [[LiveStreams docs]](https://developers.google.com/youtube/v3/live/docs/liveStreams) [[RTMPS ingestion guide]](https://developers.google.com/youtube/v3/live/guides/rtmps-ingestion).
- **Chat/comments**: `liveChatMessages.list`/`.insert` confirmed **poll-only — no webhook/push option exists** for live chat, matching what's implemented (`YoutubeAdapter.fetchComments` respects the API's own `pollingIntervalMillis` from the response, floored at 10s, backing off to 60s on failure). Latency is therefore bound by YouTube's suggested polling interval, typically several seconds, not sub-second.
- **Moderation**: `liveChatBans`/`liveChatModerators` resources support banning/muting participants and assigning moderators programmatically. Not currently called by the adapter (out of scope so far). Unchanged.
- **Recording/VOD**: broadcasts are automatically archived as a standard YouTube video (assuming DVR/archiving is enabled on the broadcast), retrievable via the normal Data API. Unchanged.
- **Quota (now confirmed, was previously "pull from console")**: default project allocation is **10,000 units/day** combined for most endpoints [[Determine quota cost]](https://developers.google.com/youtube/v3/determine_quota_cost). Every **write** operation (`liveBroadcasts.insert`, `liveStreams.insert`, `liveBroadcasts.bind`, `liveBroadcasts.transition`, `liveChatMessages.insert`) costs **50 units**; **read/list** operations are cheap (1 unit). A single `publish()` call in the current adapter (insert liveStream + insert liveBroadcast + bind + one status/snippet read) burns roughly 150+ units before a single comment is polled, and `postCallToAction`'s repeat-every-5-minutes CTA resend (`ctaRepeatMs`) is another 50 units per resend. At 10,000 units/day this caps the app to **roughly 60-70 broadcasts/day project-wide** before hitting `quotaExceeded` — confirms the original doc's caution and gives it a concrete number; the adapter already handles this gracefully (`exhaustedDay` tracking + a clear `quotaMessage` error) rather than failing silently. A quota-increase request via the Google Cloud Console API dashboard remains necessary before scaling past a pilot cohort.
- **Verdict feed into 04**: full one-click capability, **implemented** (`YoutubeAdapter`) and working end-to-end against real endpoints, still contingent on a quota increase before scaling past ~1 broadcast/agent/day at current per-agent-connection-less (single shared project credential) design, and on finishing the per-agent OAuth migration described in `docs/18`.

## Zoom

- **Ingest role**: Zoom is used as a **source**, not a broadcast destination. The built-in **Live Streaming app** lets a host push a meeting/webinar to up to three simultaneous RTMP targets (Facebook, YouTube, Twitch, or custom RTMP) [[Zoom multistream]](https://onestream.live/blog/multistream-your-zoom-meetings-webinars-for-wider-outreach/).
- **REST endpoint (confirmed, more precise than original doc)**: the meeting-level path is `PATCH /meetings/{meetingId}/livestream`, taking `stream_url`, `stream_key`, and `page_url` (a URL shown to viewers with a "watch on our site" link); a companion `PATCH /meetings/{meetingId}/livestream/status` starts/stops the configured stream [[Zoom API Reference]](https://developers.zoom.us/docs/api-reference/zoom-api/methods/). This is the endpoint referenced (but not yet called) in `server/src/adapters/zoom.ts`'s TODO comment — confirmed still current and matches what's planned.
- **Plan gate (confirmed)**: Custom Live Streaming is a **paid-plan-gated** feature the meeting host must have enabled on their own Zoom account/plan — the API will reject the `livestream` PATCH otherwise; this matches the adapter's doc comment and `docs/18`'s "gate on the agent's plan, surface a clear error if custom live streaming is off" guidance. No official Zoom pricing-tier table enumerating exactly which paid plans include it was found in this pass — worth a direct Zoom sales/docs check before relying on a specific plan name in user-facing copy.
- **SDK path**: **Zoom Video SDK** supports RTMP live-streaming output from a Video SDK session (`liveStreamClient.startLiveStream()`, taking a `streamUrl`, key/token, and `broadcastUrl`) — useful for scaling an interactive session (e.g., agent + a small group on a private valuation call) beyond the 1,000-participant real-time cap by relaying the output onward [[Video SDK live streaming]](https://developers.zoom.us/docs/video-sdk/web/live-stream/) [[Zoom dev blog: live-stream with Video SDK]](https://developers.zoom.us/blog/how-to-live-stream-with-video-sdk/).
- **Auth**: per-agent **Zoom OAuth (User-managed)** app, as designed in `docs/18` §2.3 and now implemented in `server/src/oauth/zoom.ts` for account-linking — confirmed as the right auth mode for a per-agent "their own Zoom account" model rather than Server-to-Server OAuth (which authenticates as the *app owner's* account, not the agent's).
- **Chat**: Zoom's in-meeting chat and Q&A (webinar) APIs/webhooks are separate from any RTMP-relayed destination's own chat — Lifesycle would need to capture Zoom's native chat directly via Zoom webhooks (`meeting.chat_message_sent` and similar) *in addition to* whatever chat exists on any restream destination. Unchanged; still not implemented (`ZoomAdapter.fetchComments` throws "not implemented yet"), consistent with `commentFreshness = "delayed"` in the adapter.
- **Implementation status vs. this doc's original verdict**: OAuth connect is real and working; **`publish()`/`end()`/`fetchComments()` all intentionally throw** rather than fabricate ingest data — `ZoomAdapter`'s class doc comment explains the mismatch is architectural (Zoom's RTMP direction is *outbound* from a running meeting, not an inbound key the caller controls up front like Facebook/YouTube), not just unfinished wiring. This is a deeper "not one-click" nuance than the original doc captured: even once implemented, Zoom's flow will need to create-then-start a meeting and only *then* fetch/attach a stream URL, an extra step the current `IngestInfo{rtmpUrl, streamKey}` shape doesn't cleanly model.
- **Verdict feed into 04**: feasible as a private/webinar-style ingest and relay hub; not a "social platform" destination in its own right. Confirmed still accurate — publish mechanics remain unimplemented by design, not by omission.

## LinkedIn

- **Access model**: not a self-serve public API for live streaming — **confirmed still true in September 2026, and more precisely characterized now**: LinkedIn's own "Go live using a custom stream (RTMP)" flow is a **manual Live Studio web UI feature** (`linkedin.com/help/linkedin/answer/a567506`), not a documented REST/API endpoint at all. There is no `developers.linkedin.com` live-video API surface to integrate against programmatically — "custom RTMP" access means a human logs into LinkedIn's own Live Studio and copies out a server URL + stream key by hand, which an automated one-click flow cannot drive without reverse-engineering an undocumented internal endpoint. This is a stronger form of "not one-click" than the original doc implied (it read as "review-gated API access"; it is actually "no API at all, UI-only credential retrieval") [[Go live using a custom stream (RTMP)]](https://www.linkedin.com/help/linkedin/answer/a564446/go-live-using-a-custom-stream-rtmp-?lang=en) [[Custom stream RTMP FAQ]](https://www.linkedin.com/help/linkedin/answer/a567506) [[Preferred partners chart]](https://business.linkedin.com/content/dam/me/business/en-us/marketing-solutions/products/pdfs/linkedin-live-3rd-party-broadcast-partners-chart.pdf) [[Get access via preferred partners]](https://www.linkedin.com/help/linkedin/answer/a520811).
- **Eligibility**: the Page/profile itself must first be **approved for live streaming** by LinkedIn (a review of the account, separate from any partner-app approval) before the Live Studio "custom stream" option even appears — an additional gate on top of the partner-vs-custom-RTMP choice the original doc already noted.
- **Credential timing (new detail)**: RTMP URL/stream key are only issued **shortly before the scheduled start** — up to 2 hours ahead for verified Pages, only **1 hour** ahead for unverified profiles/Pages — and preview-before-going-live is capped at 2 hours (verified) or 10 minutes (unverified). This further limits how far in advance Lifesycle could pre-fetch and cache credentials even in a partner-approved posture.
- **Scheduling constraint**: from **June 22, 2026**, LinkedIn requires all live events to be scheduled in advance (spontaneous live has been removed platform-wide), though scheduling "just minutes" ahead remains possible — confirmed unchanged and now in effect (this doc is being updated after that date) [[Advance scheduling requirement]](https://www.netinfluencer.com/linkedin-to-require-advance-scheduling-for-all-live-streams-starting-june/) [[LinkedIn Live June 2026 change]](https://www.dataslayer.ai/blog/linkedin-live-june-22-2026).
- **Path to build**: apply to LinkedIn as a broadcast-tool partner (business development / partnership approval process, not pure engineering), or integrate through one of the existing approved partners (Restream, Socialive, StreamYard, Switcher Studio — current preferred-partner roster, confirmed) as an intermediate step while awaiting direct approval.
- **Verdict feed into 04**: feasible only via approved-partner RTMP relay, and only ever as a scheduled (not instant) broadcast — sets an expectation ceiling independent of Lifesycle engineering effort. No adapter exists in `server/src/adapters/` for LinkedIn (correctly, per `registry.ts` only registering facebook/youtube/zoom) — confirmed consistent with this research.

## Instagram

- **Access model**: Instagram provides no public API for a third-party app to programmatically start a live broadcast. The only sanctioned RTMP path is **Instagram Live Producer**, a first-party Instagram tool for Business/Creator accounts, not an API surface a partner app calls on the user's behalf [[Instagram Live Producer]](https://about.instagram.com/blog/tips-and-tricks/instagram-live-producer).
- **Graph API (non-live)**: as of 2026, the Instagram Graph API supports Business/Creator accounts only (personal accounts excluded entirely — must convert), covers publishing, media retrieval, comments, and insights, but explicitly **not** arbitrary live-broadcast control [[Instagram Graph API 2026 guide]](https://www.netrows.com/blog/instagram-graph-api-guide-2026).
- **Limits**: roughly 200 API calls/hour and a hard cap of 25 published posts per 24 hours per account (Reels/Stories share the same bucket) [[Instagram API Pricing 2026]](https://www.getphyllo.com/post/instagram-api-pricing-explained-iv).
- **Verdict feed into 04**: no one-click path exists. Best available integration is agent-native start (agent goes live inside Instagram) with Lifesycle assisting pre/post-event, and pulling comments/insights after the fact through the standard Graph API within its rate limits.

## TikTok

- **Access model**: **no official public API for live streaming or live chat exists**. Everything currently used by third parties (`tiktok-live-connector`, `TikTokLive` Python package, `tik.tools`) reverse-engineers TikTok's internal WebCast protocol without TikTok's sanction [[TikTokLive GitHub]](https://github.com/isaackogan/TikTokLive) [[TikTok LIVE API guide]](https://www.eulerstream.com/what-is-tiktok-live).
- **Stability risk**: in January 2026, TikTok simultaneously revoked third-party PC streaming access for Streamlabs, StreamElements, and Restream.io; TikTok acknowledged the disruption without explaining or reversing it at time of writing [[Streamlabs access revoked]](https://support.streamlabs.com/hc/en-us/articles/35259691237147-Streamlabs-x-TikTok-Streaming-Access-Revoked-Suspended).
- **TikTok Business API**: exists but is scoped to **ads and shop analytics only** — not live-broadcast or live-chat data.
- **Verdict feed into 04**: no dependable integration path. Any TikTok chat-capture feature must be built as an optional, clearly-labelled experimental add-on that can be disabled without notice, never a core dependency.
